# Standards

The user steers and agents write the code, so tools take the place of a human
code review. `orchi-standards` gives a project `ENGINEERING.md` and blocking
checks from Orchi's defaults. A new project has no setup Epic: its first run adds
the core checks, each later change adds a check when it first needs one, and a
project meant to last gets a hardening Epic beside the product work; an existing
project gets a standards Epic after an audit. `standards.py` keeps the checks
from being lowered quietly.

## Structure

| Part | Defined in |
| --- | --- |
| Premise, product constraints, default stack, check catalog, gate integrity, audit sorting | `skills/orchi-core/references/standards.md` |
| New-project and audit routes | `skills/orchi-standards/SKILL.md` |
| The `ENGINEERING.md` template with the default Checks table | `skills/orchi-core/assets/standards/ENGINEERING.md` |
| `check` and `ruleset` | `skills/orchi-core/scripts/standards.py` |
| Checks on pull requests and the weekly drift run | `skills/orchi-core/assets/github/workflows/orchi-standards.yml`, installed with `--github` |

## Decisions

Only decisions that still hold. Replace an entry when its decision changes;
delete it when it no longer holds.

| Decision | Reason | Rejected | Since |
| --- | --- | --- | --- |
| `orchi-standards` serves existing projects (an audit, a check of `ENGINEERING.md`, or hardening when a project becomes meant to last); for a new project it continues into `orchi-plan`, whose first run sets the standards, and only `orchi-plan` closes an Exploration | A new project needs no standards plan before its first code, and deriving the stack twice let the two drift | Closing the Exploration from `orchi-standards`; a separate standards step before planning a new project | [#49](https://github.com/nkhus/orchi/pull/49), [#57](https://github.com/nkhus/orchi/pull/57) |
| The user is asked only product constraints; Orchi applies the defaults for stack, tools, thresholds, and layout without asking and records why | The user never reads the code and cannot weigh tooling choices | Orchi confirming the stack with the user | [#44](https://github.com/nkhus/orchi/pull/44) |
| No Epic sets the checks up ahead of the code: each lands, with its `ENGINEERING.md` row and CI job, in the first Task whose change needs it (the `Lands with` column); the core checks (format, lint and its limits, types, tests, secrets, and `standards.py check`) come with the first code in every project; coverage, acceptance and accessibility tests, the design detector, module boundaries, dead code, dependency, static analysis, and license checks, Dependabot, and mutation tests come only in a project meant to last, through a hardening Epic, planned from a `needs-planning` Issue blocked by the first run once there is code to check and blocking nothing, and then with the first Task that needs each, which names adding it in its requirements | In a live run the foundation took an hour and two thirds of the tokens before anything the user could run, for a proof of concept; even its one-Task successor built a gated empty app; the core checks are cheap, and the rest guard a codebase that lives | A foundation Epic, of five Tasks and then one, blocking the product code; every check from the first commit | [#44](https://github.com/nkhus/orchi/pull/44), [#55](https://github.com/nkhus/orchi/pull/55), [#57](https://github.com/nkhus/orchi/pull/57) |
| One strict TypeScript stack for web apps, services, and CLIs; Python for data and ML | Static types are the cheapest check an agent gets, and one language keeps one toolchain | Choosing the language per project | [#44](https://github.com/nkhus/orchi/pull/44) |
| CI runs on every pull request, whatever its base, and a dev lead pushes a writer's commit without rerunning its checks locally | Delivery relies on CI for each Task, so an Epic PR into an Initiative branch must be checked too | CI only on pull requests into main | [#55](https://github.com/nkhus/orchi/pull/55) |
| Lowering a threshold, turning off a rule, adding a suppression, skipping or deleting a test, or changing what a check runs is a review blocker unless `ENGINEERING.md` records an exception with its reason and expiry; agents decide exceptions (the writer records the one its Task names or reports another, the dev lead decides it, and the review confirms no change avoids it), and the user hears of each in plain words as information; writers check their own diffs and the review checks the range, and no script guesses at it | An agent under pressure to pass a check can weaken the check instead; a heuristic ratchet both missed real bypasses and blocked normal work; the user cannot weigh a license or a lint rule | `standards.py ratchet`, removed after an independent review bypassed it many ways; asking the user to decide an exception, which in a live run put a dependency's license to a user who never reads code | [#44](https://github.com/nkhus/orchi/pull/44), [#48](https://github.com/nkhus/orchi/pull/48), [#55](https://github.com/nkhus/orchi/pull/55) |
| In a project meant to last, after a PR that changes the blocking checks merges into main, the delivering session applies or replaces the branch ruleset with `gh` without asking (for a standards Epic, the scope the user agreed includes it), and tells the user; when GitHub refuses, it says in one line what enforcing the checks needs; a proof of concept gets none | The ruleset makes the agreed checks binding, a step no skill owns never happens, and the user cannot weigh it; a disposable demo gains nothing from it | Asking the user once; printing the command for the user to run | [#44](https://github.com/nkhus/orchi/pull/44), owner in [#47](https://github.com/nkhus/orchi/pull/47), [#55](https://github.com/nkhus/orchi/pull/55), [#57](https://github.com/nkhus/orchi/pull/57) |
| A weekly workflow runs the slow checks and opens one Issue with what slipped | Drift appears without anyone asking, and no session starts unattended | Checking drift only when the user asks | [#44](https://github.com/nkhus/orchi/pull/44) |
| Orchi ships an `ENGINEERING.md` template with the default Checks table, not tool configuration files; the Task that adds a check writes its configuration with current tool versions, and shows it failing on a planted violation only when the configuration is the project's own | Configuration files in Orchi would go stale between releases; `check` ties the written ones to CI; a stock tool's failure needs no proof, and proving each one cost a foundation most of its time | Shipping per-ecosystem configuration templates; a planted violation for every check | [#44](https://github.com/nkhus/orchi/pull/44), [#57](https://github.com/nkhus/orchi/pull/57) |
| `ENGINEERING.md` lands with the checks it declares, in the first run, a hardening or standards Epic, or the Task that adds a check; `orchi-standards` only plans | A declared check without its job would fail `check` and mislead the next session | Writing `ENGINEERING.md` ahead of the checks | [#44](https://github.com/nkhus/orchi/pull/44), [#57](https://github.com/nkhus/orchi/pull/57) |
| Static analysis defaults to Semgrep CE, with CodeQL where GitHub Code Security is available; production dependencies' licenses are checked against a command-line allowlist that includes CC-BY-4.0, MPL-2.0, and BlueOak-1.0.0 | The defaults must work in private repositories without paid features, and a narrower list failed every Next.js app on `caniuse-lite` and `axe-core` | CodeQL as the only default | [#44](https://github.com/nkhus/orchi/pull/44), [#55](https://github.com/nkhus/orchi/pull/55) |
| A new project's first Epic, or Task, is its first run, marked `First run of <product>.` in its Issue: the thinnest slice the user can open that does the core action end to end on seeded data through the real services the exploration proved; it scaffolds the stack, and it blocks the work that writes product code, while the design Epic's steps with the user run beside it and only its builds wait, as its UI design field records; acceptance evidence is the running app until the acceptance harness lands | The user learns early whether the product can run at all, and the checks still exist before the second change; in a live run nothing tested the product's riskiest dependency until after the foundation | A foundation Epic of checks around an empty app; blocking the design Epic on it; the design Epic scaffolding the stack | [#44](https://github.com/nkhus/orchi/pull/44), [#55](https://github.com/nkhus/orchi/pull/55), [#57](https://github.com/nkhus/orchi/pull/57) |
| Orchi borrows ideas from other standards projects and depends on none | They keep their own state folders, and Spec Kit's constitution overrides the repository's own instructions, which conflicts with Git and Issues as the only shared state | Adopting BMAD, Spec Kit, or Kiro steering; copying Trail of Bits' share-alike text | [#44](https://github.com/nkhus/orchi/pull/44) |
