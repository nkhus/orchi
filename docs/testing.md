# Testing

## Deterministic validation

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements-dev.txt
python tools/validate_package.py
python -m pytest -q
```

`tools/validate_package.py` checks skill metadata (the pool entry `orchi` is explicit-only; `orchi-core`, the crew role skills, `orchi-work`, and `orchi-dashboard` may be invoked by the session and are hidden from the slash-command menu), that every subagent role renders to a Claude Code agent that carries its instructions, local Markdown links and their heading anchors through the `knowledge.py` lint (installed references must stay inside the bundle), Python syntax, standard-library-only installed scripts, JSON/YAML syntax, the npm publish allowlist (every file the installer copies must match a `files` entry, every entry must match a file, and nothing else is published), no Cyrillic text, and absence of product release markers. The CI workflow in `.github/workflows/ci.yml` runs this validation, the test suite, and `knowledge.py lint` on every pull request and every push to main; it belongs to this repository and is not installed.

Role tests cover rendering, YAML escaping, placeholder substitution, rejection of malformed roles, and that `orchi-designer` designs with the project's engine (Hallmark or prototype) in Variant, Task, and Audit modes, follows prototype's `SKILL.md` by reading it, never installs a design skill, never asks the user, and leaves the steps that need the user to the session that talks to them. Installer tests cover a clean update that keeps no backup, the design skills fetched from local Git repositories at their pinned commits (recorded by hash, updated in place, a local edit or an unrecorded copy needing `--replace-orchi`, removed on uninstall, a fetch failure or a commit mismatch changing nothing, the `.gitignore` section), the migration that removes the Impeccable Orchi installed with a backup and keeps a user's own and `.impeccable/`, the design workflow removed on update, the design workflow's pin, the dry-run label plan, project and user scopes with the rendered subagents, managed instruction preservation and removal, a `CLAUDE.md` link to `AGENTS.md`, rollback, backups on explicit replacement, symlink refusal, removal of skills a release no longer ships on update in both scopes, in a dry run's plan, and on uninstall (an edited copy needs `--replace-orchi` and blocks uninstall), migration from the shared multi-assistant layout (skills, links, instruction sections, Codex agents and configuration, edits, and direct removal), and reinstallation from an installed bundle without a source checkout. The `--github` tests cover managed template and workflow files, opting out of and back into the documentation check workflow, extending an existing PR template, conflicts, persistence, and reporting when labels cannot be created. Issue template tests check that the forms are valid with unique field ids, that every readiness checklist item maps to a Task, Epic, or Initiative field, and that the Exploration form prepares Initiative readiness items 1–5 for planning. Packaging tests prove, on a disposable copy of the source, that a renamed heading and an installed file missing from the npm `files` list fail validation, and, when npm is available, that `npm pack --dry-run` publishes exactly the files validation expects. Knowledge tests cover snapshot isolation, exact reads with hash checks, corpus scope, link/anchor validation, new-error-only linting against a base ref, and the documentation impact check. Design tests check, as text, that planning's design depth, the UI readiness items and form fields, the designer crew's role, routing, and mode rule, the Exploration's Product section, the designer routing and audit in delivery, and the user's approval of `DESIGN.md`, generated assets, and committed surface briefs agree across the references, skills, roles, and forms. Pool tests check that the session, message, answer, claim adoption, branch handover, one-Orchi takeover, own-id, mode, release and rename, and label wording stays consistent across the pool reference, `orchi`, `orchi-work`, `orchi-explore`, `orchi-plan`, and `orchi-deliver`, that no skill refers to the former team hubs, that sessions are started only in the user's turn, and that only `delivery-ready` work reaches a dev lead; they compare text, not behavior. Delivery tests check, also as text, that writers are continued rather than restarted, that two misses change course and an Initiative steps back after each Epic, that planning checks declined work, that the acceptance verdicts reach the PR template, and that `orchi-researcher` clones dependency source only outside the repository and never runs it. Standards tests run `standards.py` against disposable Git repositories: `check` passes when every declared check has its CI job, command, and configuration and fails on each missing piece, an unscheduled weekly job, and an expired or undated exception; `ruleset` requires the blocking jobs by their status check names; and the `ENGINEERING.md` template parses and declares no design check. Context tests run `knowledge.py work` against a disposable Git repository, which finds any file under `docs/work/` and exits by its findings; a text test checks that working folders, decision fates, promotion, and the review's documentation checks agree across the references, skills, and workflows. Consistency tests check, as text, that the places a session follows agree with the references: the reviewer's role carries the standards and documentation checks, `orchi-deliver`'s steps move working documents, run the documentation checks, fill Exceptions, and own the ruleset question, Orchi picks up a requested `needs-planning` Issue once unblocked, an exploration's folder goes to its first item, a worker's `done` carries its full report, plans do not stall (Initiatives, design Epics, next-step lines, resumed claims, merged PRs) and user-only questions stay with the user, and the GitHub, execution, design, and role references agree on branches, labels, PR sections, and readiness items. Status tests cover readiness classification (ready, check, blocked, claimed), standalone Task selection, ordering, and pagination against a fake `gh`.

## Installed-skill smoke test

```bash
python tools/smoke_install.py --out /tmp/orchi-installation
```

Add `--github` to also install and check the GitHub setup files and the documentation impact check; label creation reports an error in the disposable project because it has no GitHub remote. The output directory must not exist. The default `--installer npm` mode runs the npm wrapper in a new Git project, checks that existing user files (including an `AGENTS.md`) survive, that `.claude/agents/` received exactly the six Orchi subagents, that Hallmark and prototype were installed at their pinned commits and recorded in the manifest, with no Impeccable or design workflow (this mode reaches GitHub and npm), and nothing was written outside Claude Code locations, and runs the installed knowledge tool. `--installer local` uses the Python installer directly. `--installer skills` checks the third-party Skills CLI, which does not install Orchi's managed instruction sections.

## Live behavior

Tests do not establish that Claude Code follows the workflow. When changing the skill or role text, try it in a disposable repository: a read-only question, a small fix, an Epic with Tasks, an exploration with `orchi-explore` handed to `orchi-plan`, a session pool (below), and `orchi-plan` and `orchi-deliver` with delegation to the subagents. Check that the assistant researches and agrees scope before creating branches or Issues, uses the right branch and label conventions, and does not merge without authority. In delivery, check that a review defect in a writer's Task goes back to that writer by `SendMessage` and the writer adds a commit on the same branch; that a Task a writer misses twice is split, reassigned, or settled in the Issue rather than restarted with a longer brief; that an Initiative reports a step back after each Epic merge; and that the PR's Verification gives each acceptance claim a verdict. In planning, check that a request matching an Issue closed as not planned is proposed with the earlier reason.

For a session pool in Claude Desktop, check that:

- `/orchi` in a session that is not in bypass permissions mode stops and asks to switch; in bypass mode it titles itself `Orchi`, files itself into `Orchi pool · <repo>`, and starts no session; a request starts its crew in that turn, detached and filed into `Orchi pool · <repo>`; a planner continues with the first item it planned, and other ready items get start cards that start their crews with one click; a finished crew is archived;
- turning autonomous mode on, by message or with the button at the end of Orchi's report, starts the dashboard and 3 crews in one turn; one click on `Create workers` in each starts 3 workers nested under it, and a crew that cannot show a button proposes cards or asks for a reply;
- asking for the dashboard starts it as a top-level session in the group, not nested under Orchi; its page changes only when the user clicks `Refresh` or Orchi sends `refresh` or a mode, and no timer exists;
- a designer's or researcher's variants, wireframes, and clones land in `.orchi-tmp/` in its worktree, and no session waits for permission to write outside it;
- `/orchi` in a second session leaves the pool to its Orchi and links to it; after that Orchi is archived, it takes the pool over and every crew accepts;
- every crew and worker brief carries the sender's real session id;
- no session is started in a turn a message or an event started;
- five todos named while testing become `needs-planning` Issues in the user's words, Orchi reads no code for them, and those of one area go to one planner as `#<m> queued`; the planner takes them in order, and `Plan #<m> in parallel` starts a sub-planner nested under it that reports to it and is archived when planned;
- an idea goes to a researcher crew and a request to a planner crew, each titled `[<role>] <topic>`, and the crew asks the user directly while autonomous mode is off;
- "take #n" on `delivery-ready` work goes to a dev lead crew, and "take #m" on work without it is refused with the reason;
- a dev lead gives each Task to a worker, runs Tasks on different files in parallel on `task/*` branches, merges them into the Epic branch after its checks, clears each worker after its `done`, and sends a review defect, on its reopened Task, to a free worker;
- a dev lead's follow-up goes to a planner crew and comes back planned to a dev lead without the user asking;
- after `/compact` in Orchi, a crew, and a worker mid-task, asking "who are you and what is next?" gets the role and the next step, or the owner's re-sent message restores it;
- an Epic with more Tasks than workers keeps moving because a worker takes the next Task after `done`, and a worker's branch is free for its dev lead's merge after `done`;
- with autonomous mode on, a researcher's, planner's, and designer's questions are answered by Orchi's `answer` message from the crew's recommendation, and a `(user)` question about money, access, a deploy, or a destructive action still reaches the user;
- workers are released only after the PR with their work is merged, return to a detached default branch, and are cleared by their crew; a released pool crew clears itself and Orchi renames it back to `crew-<k>` on its `released` reply, with no other event needed; only crews started on demand are archived, and nothing is deleted;
- a clear refused because the session is open on screen is retried later;
- the slash-command menu offers only `/orchi`; in a session outside the pool, an implementation request gets an answer pointing to `/orchi`, not a plan or a branch, and a role skill invoked without `--report-to` stops with the same pointer;
- from scratch: an exploration of a product with a user interface fills its Product section; the plan is a first run, a standalone `design` Epic, and the rest as an Initiative whose UI Epics are blocked by the design Epic (or, when the rest is one UI Epic, a `needs-planning` Issue blocked by it); after the direction is picked the researcher runs the design session: the screen map and key-screen briefs, prototype wireframes of three or four panels per key screen with rounds until the user approves one, references the user names plus five to seven it proposes, the engine round on the first key screen (Hallmark's three themes and prototype's three variants, shown blind on the design board), and a clickable mockup in Mockup mode; the user's ratings and picks are read from the board without pasting; the designer crew then starts while the first run is built, copies the approved files into `docs/design/` without asking again, writes `PRODUCT.md`, designs only the surfaces the session left out, and never names references, picks the engine or a direction, or approves a comp itself, also in auto mode; it reports `waits for` until the first run merges, then its workers build the approved surfaces on that stack without asking the user; `DESIGN.md` is written last; the Initiative's non-UI Epics start once the first run merges, its dev lead reports `waits for` the design Epic and is woken by `merged`, and its UI Epics resolve their deferred fields from `DESIGN.md`, the surface briefs, and the comps;
- a redesign records the incumbent look in `DESIGN.md`, runs the engine round again, replaces `DESIGN.md` after the user approves the new direction, and its rollout Tasks build against it;
- a feature at design depth brief gets references and a surface brief from the planner during planning, a direction round with the project's engine when its composition is open, and is delivered with the designer's audit in its review;
- a worker in `design` mode, and an `orchi-designer` in Variant mode, give the design skill the brief as settled input and send its questions to the crew instead of asking the user; `orchi-designer` follows prototype's `SKILL.md` without starting it through the Skill tool;
- from scratch, an exploration whose direction depends on an external service or model proves it with a prototype before shaping, without asking; the first run asks only product constraints, boots the core action end to end with the core checks in CI and no planted-violation proofs for stock tools, and the user can open it from the `see it at` link; a proof of concept gets no ruleset and lists review `major` findings as follow-ups; in a project meant to last the ruleset is applied without a question after a change to the blocking checks, and a hardening Epic runs beside the product work; an exception a later PR adds is decided by the dev lead and appears in plain words in the PR and in Orchi's report, with no question to the user;
- no session asks the user a technical question: a planner shows the plan as what the user will see and do, and a dev lead pushes a writer's commit without rerunning its checks locally;
- an exploration keeps its findings as files on `explore/<slug>`, planning continues on a branch created from it with the plan in the same folder and a fate for every decision, an Epic merge moves settled content into area and behavior pages, and the final PR into main deletes the folder and passes `knowledge.py work`; a replaced decision disappears from its area page;
- an audit of an existing repository writes nothing by itself, sorts its `CLAUDE.md` rules, and proposes one standards Epic in product terms;
- a crew ignores an `autonomous` message from any session but Orchi; with autonomous mode on, Orchi merges a reviewed PR with passing checks, still asks the user before any deploy, lists the product and design decisions it made, and tells each waiting question once.
