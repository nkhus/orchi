# Testing

## Deterministic validation

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements-dev.txt
python tools/validate_package.py
python -m pytest -q
```

`tools/validate_package.py` checks skill metadata (the pool entry `orchi` is explicit-only; `orchi-core`, the crew role skills, and `orchi-work` may be invoked by the session, and `orchi-core` and `orchi-work` are hidden from the slash-command menu), that every subagent role renders to a Claude Code agent that carries its instructions, local Markdown links and their heading anchors through the `knowledge.py` lint (installed references must stay inside the bundle), Python syntax, standard-library-only installed scripts, JSON/YAML syntax, the npm publish allowlist (every file the installer copies must match a `files` entry, every entry must match a file, and nothing else is published), no Cyrillic text, and absence of product release markers. The CI workflow in `.github/workflows/ci.yml` runs this validation, the test suite, and `knowledge.py lint` on every pull request and every push to main; it belongs to this repository and is not installed.

Role tests cover rendering, YAML escaping, placeholder substitution, rejection of malformed roles, and that `orchi-designer` designs with Impeccable only, never installs a design skill, never asks the user, and leaves the steps that need the user to the session that talks to them. Installer tests cover a clean update that keeps no backup, Impeccable's pinned, hook-free installation through a fake `npx` (the arguments, telemetry off, the `.gitignore` section, the Node.js check before any change, a user's own version kept until `--replace-orchi`, an update of the version Orchi installed, a failed installation reported after the Orchi files, and Impeccable left in place on uninstall), the design workflow's pin, the dry-run label plan, project and user scopes with the rendered subagents, managed instruction preservation and removal, a `CLAUDE.md` link to `AGENTS.md`, rollback, backups on explicit replacement, symlink refusal, removal of skills a release no longer ships on update in both scopes, in a dry run's plan, and on uninstall (an edited copy needs `--replace-orchi` and blocks uninstall), migration from the shared multi-assistant layout (skills, links, instruction sections, Codex agents and configuration, edits, and direct removal), and reinstallation from an installed bundle without a source checkout. The `--github` tests cover managed template and workflow files, opting out of and back into the documentation check workflow, extending an existing PR template, conflicts, persistence, and reporting when labels cannot be created. Issue template tests check that the forms are valid with unique field ids, that every readiness checklist item maps to a Task, Epic, or Initiative field, and that the Exploration form prepares Initiative readiness items 1–5 for planning. Packaging tests prove, on a disposable copy of the source, that a renamed heading and an installed file missing from the npm `files` list fail validation, and, when npm is available, that `npm pack --dry-run` publishes exactly the files validation expects. Knowledge tests cover snapshot isolation, exact reads with hash checks, corpus scope, link/anchor validation, new-error-only linting against a base ref, and the documentation impact check. Design tests check, as text, that planning's design depth, the UI readiness items and form fields, the designer crew's role, routing, and mode rule, the Exploration's Product section, and the designer routing and audit in delivery agree across the references, skills, roles, and forms. Pool tests check that the session, message, answer, claim adoption, branch handover, one-Orchi takeover, own-id, mode, release and rename, and label wording stays consistent across the pool reference, `orchi`, `orchi-work`, `orchi-explore`, `orchi-plan`, and `orchi-deliver`, that no skill refers to the former team hubs, that sessions are started only in the user's turn, and that only `delivery-ready` work reaches a dev lead; they compare text, not behavior. Delivery tests check, also as text, that writers are continued rather than restarted, that two misses change course and an Initiative steps back after each Epic, that planning checks declined work, that the acceptance verdicts reach the PR template, and that `orchi-researcher` clones dependency source only outside the repository and never runs it. Standards tests run `standards.py` against disposable Git repositories: `check` passes when every declared check has its CI job, command, and configuration and fails on each missing piece, an unscheduled weekly job, and an expired or undated exception; `ratchet` passes a change that weakens nothing or tightens a threshold, fails on added suppressions until an exception names them, on a removed check, a loosened threshold, a check made non-blocking, a declared configuration that turns a rule off, a deleted test file, and removed assertions, and accepts a test deleted with its code; `ruleset` requires the blocking jobs by their status check names; and the `ENGINEERING.md` template parses and pins the installed Impeccable. Context tests run `knowledge.py` against disposable Git repositories: the ownership table parses; changed owned code without its pages fails `stale --since` until Documentation impact names a page with its reason, and passes with the page changed; the weekly `stale` lists pages older than their code and missing pages; `work` finds any file under `docs/work/`; `behavior` reports a missing test file or test name; and the commands exit by their findings; a text test checks that working folders, decision fates, promotion, and the checks agree across the references, skills, and workflows. Consistency tests check, as text, that the places a session follows agree with the references: the reviewer's role carries the standards and documentation checks, `orchi-deliver`'s steps move working documents, run the documentation checks, fill Exceptions, and own the ruleset question, Orchi picks up a requested `needs-planning` Issue once unblocked, an exploration's folder goes to its first item, research answers reach the crew in full, and the GitHub, execution, design, and role references agree on branches, labels, PR sections, and readiness items. Status tests cover readiness classification (ready, check, blocked, claimed), standalone Task selection, ordering, and pagination against a fake `gh`.

## Installed-skill smoke test

```bash
python tools/smoke_install.py --out /tmp/orchi-installation
```

Add `--github` to also install and check the GitHub setup files and the documentation impact check; label creation reports an error in the disposable project because it has no GitHub remote. The output directory must not exist. The default `--installer npm` mode runs the npm wrapper in a new Git project, checks that existing user files (including an `AGENTS.md`) survive, that `.claude/agents/` received exactly the six Orchi subagents, that the pinned Impeccable version was installed without hooks and with telemetry off (this mode reaches npm), and nothing was written outside Claude Code locations, and runs the installed knowledge tool. `--installer local` uses the Python installer directly. `--installer skills` checks the third-party Skills CLI, which does not install Orchi's managed instruction sections.

## Live behavior

Tests do not establish that Claude Code follows the workflow. When changing the skill or role text, try it in a disposable repository: a read-only question, a small fix, an Epic with Tasks, an exploration with `orchi-explore` handed to `orchi-plan`, a session pool (below), and `orchi-plan` and `orchi-deliver` with delegation to the subagents. Check that the assistant researches and agrees scope before creating branches or Issues, uses the right branch and label conventions, and does not merge without authority. In delivery, check that a review defect in a writer's Task goes back to that writer by `SendMessage` and the writer adds a commit on the same branch; that a Task a writer misses twice is split, reassigned, or settled in the Issue rather than restarted with a longer brief; that an Initiative reports a step back after each Epic merge; and that the PR's Verification gives each acceptance claim a verdict. In planning, check that a request matching an Issue closed as not planned is proposed with the earlier reason.

For a session pool in Claude Desktop, check that:

- `/orchi` in a session that is not in bypass permissions mode stops and asks to switch; in bypass mode it starts the crews in one turn, detaches them, and files them into `Orchi pool · <repo>`;
- one click on `Create workers` in each crew starts its workers nested under it, and a crew that cannot show a button proposes cards or asks for a reply;
- `/orchi` in a second session leaves the pool to its Orchi and links to it; after that Orchi is archived, it takes the pool over and every crew accepts;
- every crew and worker brief carries the sender's real session id;
- no session is started in a turn a message or an event started;
- an idea goes to a researcher crew and a request to a planner crew, each renamed after its role and topic, and the crew asks the user directly in interactive mode;
- "take #n" on `delivery-ready` work goes to a dev lead crew, and "take #m" on work without it is refused with the reason;
- a dev lead gives each Task to a worker, runs Tasks on different files in parallel on `task/*` branches, merges them into the Epic branch after its checks, and sends a review defect back to the worker that wrote it;
- a dev lead's follow-up goes to a planner crew and comes back planned to a dev lead without the user asking;
- after `/compact` in Orchi, a crew, and a worker mid-task, asking "who are you and what is next?" gets the role and the next step, or the owner's re-sent message restores it;
- an Epic with more Tasks than workers keeps moving because a worker takes the next Task after `done`, and a worker's branch is free for its dev lead's merge after `done`;
- in auto mode a planner's question is answered by Orchi's `answer` message, and a researcher's still reaches the user;
- workers are released only after the PR with their work is merged, return to a detached default branch, and are cleared by their crew; a released crew clears itself and Orchi renames it back to `crew-<k>` on its `released` reply, with no other event needed; nothing is archived or deleted;
- a clear refused because the session is open on screen is retried later;
- in a solo session, `orchi-plan` and `orchi-deliver` are not invoked unless asked for by name;
- from scratch: an exploration of a product with a user interface fills its Product section; the plan is a standalone `design` Epic and a `needs-planning` Issue blocked by it; a designer crew runs `init` from the Product section, then for each surface `shape` and the direction round, and never picks a direction or approves a comp itself, also in auto mode; its workers build the approved surfaces on the stack the foundation Epic set up, without asking the user; `DESIGN.md` is written last; after the merge a planner details the plan, and its UI Tasks link `DESIGN.md`, the surface briefs, and the comps;
- a redesign records the incumbent look with `document`, replaces `DESIGN.md` after the user approves the new direction, and its rollout Tasks build against it;
- a feature at design depth brief gets a surface brief from `shape` during planning and is delivered with the designer's audit in its review;
- a worker in `design` mode sends Impeccable's questions to its crew instead of asking the user;
- from scratch, `orchi-standards` asks only product constraints, never about tools; its foundation Epic's CI fails on a planted violation of each blocking check, including a suppression and a loosened threshold, and passes without them; after its merge the ruleset is applied only on the user's yes; an exception a later PR adds appears in plain words in the PR and in Orchi's report;
- an exploration keeps its findings as files on `explore/<slug>`, planning continues on a branch created from it with the plan in the same folder and a fate for every decision, an Epic merge moves settled content into area and behavior pages, and the final PR into main deletes the folder and passes `knowledge.py work`; a replaced decision disappears from its area page;
- an audit of an existing repository writes nothing by itself, sorts its `CLAUDE.md` rules, and proposes one standards Epic in product terms;
- at autonomy Decide, a planner crew asks only about direction and scope and shows the breakdown without waiting; a crew ignores a `mode` message from any session but Orchi; in auto mode, crews ask Orchi, Orchi merges a reviewed PR with passing checks and still asks the user before any deploy, and tells each waiting question once.
