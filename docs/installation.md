# Installation

## Install

Run the installer from the target repository:

```bash
npx --yes github:nkhus/orchi
```

The current directory is the installation target; `--project /path/to/project` chooses another one.

The installer installs the `orchi-core` skill (its instructions, references, subagent roles, the read-only knowledge and status tools, and the installer itself) the `/orchi` entry, and the role skills `orchi-explore`, `orchi-plan`, `orchi-design`, `orchi-standards`, `orchi-deliver`, `orchi-work`, and `orchi-dashboard`, which Orchi's sessions invoke and the slash-command menu hides. It renders the Orchi subagents, adds a managed section to `CLAUDE.md`, installs the [design skills](#design-skills), and reports whether `git`, `gh`, `node`, and `npx` are available. It does not install or authenticate Claude Code or the GitHub CLI.

Requirements: Git, which also fetches the design skills, network access to GitHub (or a [mirror](#design-skills)), the GitHub CLI (`gh`) for Issue and PR work, and Python 3.11 or newer for the bundled scripts, which use only the standard library. The Python installer does not need Node.js; the npm wrapper needs Node.js and `uv`, and Hallmark's own scripts use Node.js 18 or newer when it is present. prototype needs nothing else. Linux, macOS, and WSL are supported.

## Skills and instructions

Each skill is installed as a directory in `.claude/skills/` (`orchi-core`, `orchi-explore`, `orchi-plan`, `orchi-design`, `orchi-standards`, `orchi-deliver`, `orchi-work`, `orchi-dashboard`, `orchi`), where Claude Code discovers it. The skills move and clone with the repository.

The installer appends an Orchi workflow section to the target root `CLAUDE.md`. Its rules route implementation through the Orchi skill, require research and agreement before tracking or changes, and keep merge and deployment within the user's authority. It never copies this repository's contributor `AGENTS.md` into another project, and it does not change an existing root `AGENTS.md`. When `CLAUDE.md` is a symlink to root `AGENTS.md`, the section goes into `AGENTS.md`, which Claude Code reads through the link.

Sections are delimited by `<!-- orchi:begin -->` and `<!-- orchi:end -->` (`# orchi:begin` and `# orchi:end` in `.gitignore`). Existing content outside these markers is preserved byte-for-byte, including line endings. Reinstallation updates only an unchanged managed section and never duplicates it. Edited or malformed sections cause installation to stop before mutation, even with `--replace-orchi`; preserve custom rules outside the managed section. A managed instruction file you delete is dropped from the manifest on the next run instead of blocking uninstallation; an installation recreates it.

Instruction discovery improves routing but does not prove model compliance. More specific instructions, explicit user instructions, disabled skills, instruction-size limits, and application settings can affect behavior. Start a fresh session and verify that the skills are exposed: `/orchi` and the other entry skills in Claude Code's slash-command menu, or the IDE's skill selection interface. Every skill but `/orchi` is hidden from the menu (`user-invocable: false`); sessions load them by themselves.

In a project, a managed section in `.gitignore` ignores the worktrees of Orchi's pool sessions (`.claude/worktrees/`), the temporary files of its sessions and subagents (`.orchi-tmp/`), and the Hallmark design skill's runtime folder (`.hallmark/`, at any depth). It follows the same rules as the instruction section: an unchanged section updates on reinstall, and uninstalling removes it.

## Subagents

Each role in `.claude/skills/orchi-core/roles/` is rendered to `.claude/agents/`: `orchi-scout.md`, `orchi-researcher.md`, `orchi-implementer.md`, `orchi-fixer.md`, `orchi-reviewer.md`, and `orchi-designer.md`.

`orchi-designer` designs with the project's design engine, one of the [design skills](#design-skills) the installer installs, and follows the repository's own design system; see [design skills](../skills/orchi-core/roles/README.md#design-skills).

Rendered agents name the installed skill as `.claude/skills/orchi-core` in a project installation and by its absolute path in a user-wide one. They are recorded in the manifest with their hashes: unmodified files update in place on reinstall, a locally edited or pre-existing unmanaged file needs `--replace-orchi` (which keeps a backup), and uninstalling removes them and refuses edited ones. Agent files do not depend on `--github`.

Claude Code lets subagents start their own, up to three layers below the main conversation, by default, which is the nesting Orchi uses. Subagent models are pinned in the roles; if a pinned model is unavailable, the main session performs the step itself.

## Design skills

The installer installs two third-party Claude Code skills, both MIT-licensed, so a project can choose its design engine in its first design Epic; see [design](design.md):

| Skill | Source | Commit |
| --- | --- | --- |
| `.claude/skills/hallmark/` | `skills/hallmark` in [Nutlope/hallmark](https://github.com/Nutlope/hallmark) | `6033bab2a8051b5454552d2e8e6cb8f27c483a42` |
| `.claude/skills/prototype/` | `skills/prototype` in [emilkowalski/skills](https://github.com/emilkowalski/skills) | `2d228630ba1446365f614a108cb8252f1feda202` |

User-wide, they go to `~/.claude/skills/`. Each is installed exactly as published at its pinned commit, front matter included: prototype runs only when invoked explicitly (`disable-model-invocation: true`).

- **Fetching.** Before changing anything, including in a dry run, the installer fetches each pinned commit with Git into a temporary directory (`git fetch --depth 1 <url> <commit>`), checks that the fetched commit is the pinned one, and takes only the skill's directory from it; the temporary directory is removed afterwards. The URL is `https://github.com/<owner>/<repository>`, so the installer needs network access to GitHub. If a fetch fails, it stops with the error and changes nothing.
- **Mirrors and offline installation.** `ORCHI_DESIGN_GIT_BASE` replaces `https://github.com/` as the base: the installer fetches from `<base><owner>/<repository>` (a `/` is added unless the base ends in `/` or `:`), for example `ORCHI_DESIGN_GIT_BASE=file:///srv/mirrors/` with bare repositories at `/srv/mirrors/Nutlope/hallmark` and `/srv/mirrors/emilkowalski/skills`, or `git@github.com:` for SSH. The mirror must contain the pinned commits.
- **Management.** The manifest records each design skill's file hashes beside Orchi's own skills, and the same rules apply: an unmodified copy updates in place when a release pins another commit, a locally edited copy or one Orchi did not install needs `--replace-orchi` (which keeps a backup), and a design skill a later release no longer installs is removed.
- **Removal.** `--uninstall` removes the design skills Orchi installed and refuses edited ones; it fetches nothing. A design skill directory the manifest does not record is kept, with a note.

## GitHub setup

```bash
npx --yes github:nkhus/orchi --github
```

`--github` is opt-in and applies to project installations. Once chosen, later installations keep it. It adds:

| File or resource | Purpose |
| --- | --- |
| `.github/ISSUE_TEMPLATE/orchi-initiative.yml`, `orchi-epic.yml`, `orchi-task.yml`, `orchi-exploration.yml` | Issue forms that apply the matching type label; the Task, Epic, and Initiative forms have a field for every item of the [readiness checklists](../skills/orchi-core/references/readiness.md), and the Exploration form prepares an Initiative's first five |
| PR template section | Summary, Verification, Merge risk, Exceptions, Documentation impact, and Handoff, as a managed section in an existing template (`.github/pull_request_template.md` or another location GitHub reads) or a new one |
| `.github/workflows/orchi-docs.yml` | On every PR, fails on broken local links the PR introduces (`knowledge.py lint --since` the base branch), a missing or empty Documentation impact section (skipped for Dependabot); on a PR into the default branch, also on any file under `docs/work/` (`work`). Omitted with `--no-docs-workflow` |
| `.github/workflows/orchi-standards.yml` | When the repository has `ENGINEERING.md`: on every PR, `standards.py check` (every declared check has its CI job and configuration, and no exception has expired); weekly, the same check, keeping one open `Standards drift` Issue labelled `needs-planning` when it fails. Without `ENGINEERING.md` it passes. See [standards](../skills/orchi-core/references/standards.md). Omitted with `--no-standards-workflow` |
| Labels `Initiative`, `Epic`, `Task`, `in-progress`, `Exploration`, `needs-planning`, `delivery-ready`, `retro`, `design` | Created with `gh` when missing; existing labels are not changed |

The template and workflow files are recorded in the manifest with their hashes, so they follow the same rules as the skill: unmodified files update in place, edited or pre-existing files need `--replace-orchi`, and uninstalling refuses edited files. Label creation needs a GitHub remote and an authenticated `gh`. If either is missing, the installation still completes and reports the error in `labels`; rerun it later to create them. Uninstalling leaves labels in place.

To skip the documentation check workflow, add `--no-docs-workflow`; to skip the standards check workflow, add `--no-standards-workflow`. The manifest records each choice (`docs_workflow`, `standards_workflow`) and later installations, including an [Orchi update](../skills/orchi-core/references/pool.md#update-orchi), keep it until `--docs-workflow` or `--standards-workflow` turns that workflow back on. Opting out removes an installed, unmodified workflow; an edited one is a conflict that needs `--replace-orchi`, which keeps a backup. Without either flag, a workflow is installed, including for manifests written before its option existed. Without the standards workflow there is no weekly `Standards drift` Issue; drop the `standards` row from a project's `ENGINEERING.md`.

Broken links that already exist on the base branch are reported as pre-existing and do not fail a PR, so the workflow can be enabled in a repository with documentation debt. Run `python3 .claude/skills/orchi-core/scripts/knowledge.py lint` to see that debt. Make the check required in branch protection if it should block merges.

## Pool setup

Orchi runs as a session pool in Claude Desktop: Orchi, the entry you talk to, and crews with nested workers that do the work, as the [pool reference](../skills/orchi-core/references/pool.md) describes. `/orchi` is the only command you type. To set it up in a project:

1. Install, preferably with `--github`, so the `Exploration`, `needs-planning`, `delivery-ready`, `retro`, and `design` labels exist. You do not commit or push it: on `/orchi`, Orchi checks that the repository has a GitHub remote, a commit on `main`, the installation pushed, the labels, and `.claude/worktrees/` and `.orchi-tmp/` ignored, and a setup agent fixes what is missing in the same turn, as [Prepare the repository](../skills/orchi-core/references/pool.md#prepare-the-repository) says. It asks you only to create a missing GitHub repository, to run `gh auth login`, about a file that looks like a secret, about a diverged `main`, and to merge the setup PR when branch protection refuses its push. Planner crews add `delivery-ready` when work passes its readiness gate; Orchi gives a dev lead nothing without it.
2. Protect `main` with branch protection. The pool runs in bypass permissions mode, so its sessions run every tool without a prompt; role instructions, the dev lead's checks, the review, and branch protection are what remain.
3. In Claude Desktop, open one session in the repository, switch it to bypass permissions mode, and type `/orchi`. That session becomes Orchi: it titles itself `Orchi` and files itself into the sidebar group `Orchi pool · <repo>`, where every session it starts goes too. It starts no crew ahead of work. Ask it for a dashboard when you want one: a session of its own on Sonnet at low effort whose page updates when you click `Refresh` in it.
4. Bring every request to Orchi, also many at once while you test: it files each in your words and gives related ones to one planner, which queues them. It starts a crew session for a request, or gives it to a free pool crew, titled with its role in brackets and its topic (`[planner] pay`, `[dev-lead] pay-token`), and links you to it. Work that becomes ready while Orchi cannot start a session gets a start button in its report. While autonomous mode is off, answer the crew in its own session.
5. Ask Orchi to take planned work ("take #12"). A `design` Epic goes to a designer crew; other work goes to a dev lead crew. Follow-ups a dev lead files come back planned and are taken without asking.
6. Orchi asks you whether to merge each PR into main and merges it on your yes.
7. When you step away, turn on autonomous mode: tell Orchi, or click the button at the end of its report (`--crews <n>` and `--workers <n>` on `/orchi` choose other pool sizes). In that turn Orchi starts the dashboard and 3 crews, and one click on `Create workers` in each starts 3 workers nested under it; a session can start other sessions only in a turn you started, so these clicks are the only manual steps. Crews then ask only Orchi, which decides what you would, sends each decision as an instruction, lists the product and design decisions in its report, and merges reviewed PRs with passing checks; money, access, deploys, and destructive actions still wait for you. The mode holds through compaction until you turn it off or type `/orchi` again.
8. When work is done, Orchi archives a crew it started on demand; pool workers and crews clear themselves and return to the pool as `worker-<n>` and `crew-<k>`. Nothing is deleted.

Pool sessions run with Remote Control off, because a session served over Remote Control cannot be cleared; Orchi itself can stay on it. A clear is also refused while you have the session open on screen or pinned; the clearing session retries once, then tells you. Type `/orchi`, click `Create workers`, and ask for more crews in the desktop app: a message typed over Remote Control cannot start sessions. Rerunning `/orchi` in Orchi is safe: it finds its crews by the sidebar group and adds only what is missing. In another session it changes nothing and points you to the pool's Orchi; it takes the pool over only when that Orchi is archived or gone.

## User-wide installation

```bash
npx --yes github:nkhus/orchi --global
```

This stores the skills in `~/.claude/skills/`, renders subagents in `~/.claude/agents/`, and adds the managed section to `~/.claude/CLAUDE.md`. Instructions and rendered subagents reference the absolute skill path. No project's root files are edited in global mode. Use project installation when team sharing is required. Local home files do not provision remote or cloud environments; install in each execution environment.

## Inspect, update, and remove

```bash
npx --yes github:nkhus/orchi --project "$PWD" --dry-run
npx --yes github:nkhus/orchi --project "$PWD" --replace-orchi
npx --yes github:nkhus/orchi --project "$PWD" --uninstall
```

Dry-run lists file changes and conflicts (`conflicts`, `requires_replace`) without writing; with `--github` it also lists the labels the installation would create (`labels.create`), read with `gh` and never created. A manifest at `.claude/.orchi-install.json` records hashes, options, managed files, and managed sections. Identical installation is a no-op. Rerunning the installer updates unmodified managed files. Skill files edited since installation, or unmanaged files in the Orchi destination, require `--replace-orchi`. When an installation replaces content Orchi did not install unchanged (edited files, or existing files such as a `CLAUDE.md` it adds a section to), the replaced files are backed up beside the project, or inside the home directory for user-wide installation, and the result names the backup; a clean update of unmodified managed files keeps no backup. Skills, agents, instructions, and manifest are staged together and rolled back on an ordinary installation error. A process or host crash during mutation requires inspecting the backup and target before retrying.

The installer refuses symlinked skill destinations, symlinked agent files it manages, and instruction symlinks other than `CLAUDE.md` linking to root `AGENTS.md`. It preserves unrelated skills and agents, settings, and application manifests. Do not alternate installers to manage the same installation.

`--uninstall` removes the complete managed Orchi installation at the selected project/user scope, including its instruction and `.gitignore` sections. It preserves surrounding user instructions and refuses modified skill files or managed sections. It does not remove Claude Code, authentication, GitHub Issues, branches, backups, or design skills Orchi did not install.

Commit the project skill files, rendered agents, instruction changes, and the installation manifest when sharing the setup with the team; in a pool, Orchi's setup agent commits and pushes them on `/orchi`.

## Local and offline installation

From a checkout:

```bash
python3 tools/install.py --project /absolute/path/to/project --dry-run
python3 tools/install.py --project /absolute/path/to/project
```

The Python installer uses only the standard library. The npm wrapper invokes the same implementation through `uv`. An installed bundle can reinstall or remove itself without a source checkout:

```bash
python3 .claude/skills/orchi-core/scripts/orchi_install.py --project "$PWD"
```

## Upgrading

In a project that runs Orchi, tell Orchi "update Orchi", or click `Update Orchi` when it offers a newer version on `/orchi`. It tells you what changes, and on your yes installs the new version on `main`, moves every session to it without losing its conversation or work, and carries out what the upgrade notes below ask of a project, as the [pool reference](../skills/orchi-core/references/pool.md#update-orchi) says. A project installed before 0.37 is updated this way once it runs 0.37; update it to 0.37 by hand first.

Without Orchi, rerun the installation command. The manifest records the installed version; `python3 .claude/skills/orchi-core/scripts/orchi_install.py --version` prints it with the bundled version and the upgrade command. An installed copy cannot fetch a newer version, so upgrades come from `npx` or a source checkout. Running from the installed copy still treats local edits to the installed skills as conflicts; there, `--replace-orchi` records the edited copy as installed.

The dashboard is no longer started on `/orchi`: ask for one, or turn on autonomous mode. It is a top-level session with its own worktree and refreshes only when you click `Refresh` in it, with no timer. Orchi titles itself `Orchi` and files itself into the `Orchi pool · <repo>` group; crews are titled `[<role>] <topic>`; Issues say `Requested by: Orchi`. Sessions and subagents keep temporary files in `.orchi-tmp/` in their worktree, which the managed `.gitignore` section ignores, so no write waits for your permission. A running pool keeps working; its next `/orchi` renames Orchi, and work whose `Requested by:` line names the former title waits for you to say "take #<n>".
- **Design session in exploration (0.34).** A new product's exploration now designs it with you after you pick the direction: the screen map, grey wireframes of each key screen's panels, references, the engine round, and a clickable mockup, shown on a design board where you rate and pick. Its first design Epic builds what you approved instead of asking again. Nothing to do on upgrade.
- **Sessions on demand (0.32).** `/orchi` no longer builds a pool. Orchi starts a crew session per request, which writes code through subagents and is archived when its work is done; a planner continues with the first item it planned, and other ready work gets a start button. "Prepare autonomous development" builds a pool of 2 crews of 2 workers (not 5 of 3), whose crews are cleared and reused. An existing pool keeps working as one.
- **First run instead of a foundation (0.31).** A new project has no foundation Epic. An exploration first proves with a prototype what the idea cannot work without, such as an outside service or model, without asking. The first delivery is the first run, the product's core action end to end, which also scaffolds the stack with the core checks; every other check lands with the first change that needs it, and a project meant to last gets the rest in a hardening Epic beside the product work. A proof of concept gets no ruleset, and its review lists `major` findings as follow-ups. A `major` must be a demonstrated defect with its scenario and the rule it breaks, a review may find nothing, and the one recheck looks only at the repairs, with a final verdict. A range that only changes tool configuration gets no reviewer. Workers clear their conversation after each task, so rework goes to any free worker. When a PR changes what you see, its dev lead starts the app and Orchi gives you the link with the merge question. A foundation Epic planned earlier still delivers as an ordinary Epic.
- **No commands for you (0.30).** No session asks you to run a command, open a terminal or GitHub, or edit a file: it asks for a yes and does the work. Below auto mode, Orchi asks whether to merge each PR into `main` and merges it on your yes. When `gh` is not signed in, Orchi starts the sign-in and gives you a one-time code, so you only approve it in the browser; it also merges the setup PR and GitHub's diverged default branch on your yes.
- **Shorter start, product questions only (0.29).** A new project's foundation Epic is one Task with the core checks; module boundaries, dead code, dependency, static analysis, and license checks, Dependabot, and mutation tests move to a hardening Epic planned only for a project meant to last, which runs beside the product work. The design Epic starts with the foundation, and the rest of a new product is planned at once instead of after the design. No session asks you a technical question: the planner shows the plan as what you will see and do, the dev lead decides exceptions and applies the branch ruleset without asking, and you hear of each exception as information. The license allowlist in the `ENGINEERING.md` template adds BlueOak-1.0.0, CC0-1.0, CC-BY-4.0, MPL-2.0, Python-2.0, and Unlicense for production dependencies. A dev lead no longer reruns every writer's checks locally; CI runs them. A foundation Epic planned earlier with five Tasks stays valid.
- **Dashboard (0.28).** The new hidden skill `orchi-dashboard` and the read-only `dashboard.py` script. `/orchi` adds a `dashboard` session to an existing pool and gives you its page's link; Orchi's own reports now carry only what needs you. Rerun `/orchi` in Orchi after reinstalling.
- **Repository setup (0.27).** You no longer commit or push the installation: `/orchi` checks the repository first, and a setup agent commits and pushes the installation (or, in a new repository, everything not ignored), creates missing labels, and ignores `.claude/worktrees/`. Reinstalling adds `.claude/worktrees/` to the managed `.gitignore` section.
- **One entry (0.26).** `/orchi` is the only command you type. The role skills (`orchi-explore`, `orchi-plan`, `orchi-standards`, `orchi-design`, `orchi-deliver`) are hidden from the slash-command menu and run only as Orchi's crew assignments; without one they point you to `/orchi`. Crews report to Orchi instead of printing commands for you, and a merge brings `#<n> merged` back to the crew instead of a rerun. In a session that is not part of the pool, Claude answers questions and points work to `/orchi`.
- **Design track fixes (0.25).** `DESIGN.md` is written with you (`/impeccable document`) after the last build, and a generated asset is committed only after you approve it. At design depth brief, `shape`'s result is a surface brief with a direction contract, committed on the work's branch planning creates. The designer works without `DESIGN.md` when there is none, fixes every primary `detect` finding, and has a Recheck input in Audit mode. A designer worker's decision goes to its crew as a question with screenshots. Surface briefs and approved comps count as current documentation.
- **Flows and authority (0.24).** A planner labels every top item `delivery-ready` (a `design` Epic needs no Tasks yet), and `orchi-plan` ends with one next-step line per item. Orchi checks Initiatives' blockers directly, notices merged PRs and lost crews on each wake, and never answers a question marked `(user)`: design directions, comps, assets, the branch ruleset, and PRs that add exceptions, which Auto never merges. Delivery moves documents before the review, lists every review finding with its resolution, repairs `blocker` and `major` findings, keeps a claim across a rerun, and tells you to rerun after merging. A worker's `done` carries its full report; a dev lead resolves merges and moves documents itself.
- **Simpler gates (0.23).** `standards.py ratchet` and `knowledge.py stale` and `behavior` are gone: writers check their own diffs and the review checks the range against the [gate integrity](../skills/orchi-core/references/standards.md#gate-integrity) list and the documentation map. The standards workflow's PR job is now `standards` (rename it in your ruleset's required checks), the template drops the ratchet and the two documentation rows, and the documentation workflow skips the impact check for Dependabot.
- **Consistency fixes (0.22).** `orchi-reviewer` checks `ENGINEERING.md`, the ratchet, exceptions, acceptance evidence, and the documentation checks itself, and reports exceptions for the PR; `orchi-deliver` moves working documents at each merge, runs `stale`, `behavior`, and `work`, fills the Exceptions section, and after a foundation or standards Epic asks you once to apply the branch ruleset. Orchi gives a planner a `needs-planning` Issue it requested once its blockers close. A worker's research answer carries its full report. `orchi-implementer` runs at medium effort.
- **GitHub setup.** With `--github`: the `orchi-exploration.yml` form, a `Merge risk` section and acceptance verdicts in the managed PR template, and the `Exploration`, `needs-planning`, `delivery-ready`, and `retro` labels.

### From 0.6.x to 0.7.x

Versions before 0.7.0 installed for Codex, GitHub Copilot, and Claude Code together: one copy of each skill in `.agents/skills/`, Claude links to it in `.claude/skills/`, the workflow section in root `AGENTS.md` with an `@AGENTS.md` import in `CLAUDE.md`, and, depending on the selection, a pointer in `.github/copilot-instructions.md`, Codex agents in `.codex/agents/`, and a block in `.codex/config.toml`. The manifest was `.agents/.orchi-install.json`.

Rerunning the installer migrates such an installation (project or user-wide, including the single-skill and five-skill layouts) to Claude Code only, in one staged change:

- The skills recorded in the old manifest are removed from `.agents/skills/`, and the Claude links become the skill directories themselves. Skills that the old manifest does not record are left untouched.
- The workflow section moves from root `AGENTS.md` into `CLAUDE.md`, replacing the import; the Copilot and Codex instruction sections are removed. Text outside the sections stays as it was.
- Codex agents are removed, Claude Code agents are updated, and the `.codex/config.toml` block is removed (with the file, if Orchi created it and nothing else remains). An edited block is left in place with a note in `notes`.
- The GitHub setup and the documentation check workflow choice carry over. The old manifest is replaced by `.claude/.orchi-install.json`.

Edited skills, agents, or instruction sections stop the migration as they would an upgrade: review them, then pass `--replace-orchi` for files (which backs them up first) or restore edited sections by hand. A link at `.claude/skills/<name>` to anything other than the recorded shared copy stops the installation. `--uninstall` also removes a shared-layout installation directly. Empty `.agents/skills/` and `.codex/agents/` directories may remain; remove them if nothing else uses them.

The same upgrade adds the `orchi-designer` agent, which takes UI Tasks and audits UI diffs; see [choosing a writer](../skills/orchi-core/roles/README.md#choosing-a-writer). An existing `.claude/agents/orchi-designer.md` that Orchi did not install is a conflict that needs `--replace-orchi`.

Notes for versions before 0.6 are in the Git history of this file.
