# Proportionate progressive planning

An initiative is the entire finite accepted request; an epic is the nearest jointly verifiable result; a task is a delegated execution unit. Keep one active epic and future epics outcome-level. Do not split one atomic feature into independent initiatives just to add workers.

## Select enough authoring

Inspect actual Current, code and instructions. Empty Current is valid for greenfield. For an understood bounded change, use a ChangeBrief with exact request, stable requirements, architecture/no-change statement, selected design, fixed decisions, invariants, trusted checks and tasks. `start --file brief.json` binds generated normal Intent and first Epic Plan in one human gate. `brief-expand` only creates drafts. The controller does not invent omitted decisions.

For a larger request, author Intent Markdown and an ordered requirement/architecture-linked roadmap, `intent-build`, then `begin`. Accept direction before executable work. Preserve original request bytes and distinguish Target from implemented Current. Resolve material system choices with the human; future task/file detail does not belong in the roadmap.

## Select and design one epic

Read actual `head`, accepted `integration_base`, verified `knowledge_head`, accepted Intent and completed dependency outputs. Search both views, inspect diagnostics and read exact sources. Design shared contracts before parallel implementation. Do not treat a future producer as available code.

Persist Epic Design Markdown with `addresses`/`realizes`, sequential revision and exact hash. Derive a task DAG containing outcomes, fixed decisions, invariants, allowed local choices, initial edits, source roles, failure cases, acceptance checks and escalation. Unresolved material questions block execution. An explicit investigation task may have no product writes and return observations; a knowledge-only epic has no tasks. Neither permits unapproved prototypes in product code.

Optional `write_scope` rules declare exact directories, actions and existing allowed choices. They permit bounded technical additions, never implicit public API/security/Target changes. Use fixed assumptions when equality matters and snapshot observations when compatibility may be rechecked. `artifacts` relationships are navigation/impact metadata, not read locks.

Run `plan-preflight` before presenting a design, then submit `plan`. Known sources/packet size are checked; nonexistent dependency outputs are deferred and runtime checks repeat. Preflight is not a guarantee of future environments or semantic success.

## Adapt at the correct boundary

Use `scope-acquire` only for a delegated local addition. `amend-tasks` can revise affected pending/blocked tasks and their dependent closure while shared design, acceptance, task set and unaffected contracts remain identical; unaffected workers can finish isolated validation during its gate. New shared decisions require full `amend` after workers stop.

For target changes, preserve original source/completed history and use `revise-intent` between epics. Active work must first stop/release and accept `stop-epic`. For canonical movement, use the explicit code-and-knowledge [synchronization](synchronization.md) workflow; never replace baseline fields or reuse stale final signatures.
